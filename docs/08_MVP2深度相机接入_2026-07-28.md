# MVP2 第一阶段：深度相机接入与风险验证

> 2026-07-28。前置：`docs/07_遥控与录制_2026-07-26.md`（MVP1 完成）。
>
> 本篇是 MVP2 的**风险验证阶段**：把四个可能推翻计划的未知数逐个证伪。
> 避障逻辑一行没写 —— 这是有意的，见下。

---

## 1. 为什么先做这两件事

MVP2 的常见做法是一上来写避障逻辑。这里反过来，按**风险从高到低**排：

| 序 | 风险 | 为什么排在前面 |
| --- | --- | --- |
| ① | Astra 驱动能不能跑 | 停产硬件，跑不起来整个方案要改 |
| ② | 相机流会不会拖垮平衡回路 | **可能反伤已经做好的 MVP1** |
| ③ | 制动距离多长 | 是后面所有避障策略的输入参数 |
| ④ | 车身摆动下的点云补偿 | 有难度但方案明确 |
| ⑤ | 避障逻辑与状态机 | 前四项都定了才有意义 |

前两项都是**证伪性质**的：花的时间不多，但任何一项失败都会推翻后面的计划。
先做它们，避免在错误方向上投入。

本篇把 ①~④ 全部做完，⑤ 留给下一阶段。

## 2. 风险 ①：驱动（已解除）

硬件是 **Orbbec Astra Pro**，2016 年前后的产品，早已停产。

### 设备结构：两半是分开的

```
lsusb:
  2bc5:0501  Astra Pro HD Camera   bInterfaceClass 14 (Video)   Driver=uvcvideo
  2bc5:0403  ASTRA Pro             bInterfaceClass 255 (Vendor) Driver=[none]
```

- **RGB**（`0501`）是标准 UVC，内核直接认，`/dev/video0` 开箱即用
- **深度**（`0403`）是厂商私有接口，**没有内核驱动**，必须由用户态经 libusb 操作

`Driver=[none]` 是正常的，不是故障 —— libusb 类驱动不绑定内核驱动。
但它意味着需要 udev 规则才能让非 root 打开设备：

```
SUBSYSTEM=="usb", ATTR{idVendor}=="2bc5", MODE:="0666", GROUP:="video"
```

### 两次失败，缩小了范围

**尝试 1：`ros-jazzy-orbbec-camera`（官方新 SDK）** —— 失败。

```
Name: Bootloader device,  PID: 0x0501,  SN: (空)
```

它只看到 RGB 那半，还认错成 "Bootloader device"（PID 不在型号表里的兜底标签），
**深度传感器 `0403` 根本没被枚举**。新 SDK 面向 Femto/Gemini/Astra 2，
不含 Astra Pro。

**尝试 2：`ros-jazzy-openni2-camera` + Debian 的 libopenni2** —— 失败。

```
NiViewer2:  DeviceOpen using default: no devices found
list_devices: Found 0 devices
```

Debian 的 `libopenni2` 只带 `libPS1080.so`（PrimeSense）和 `libOniFile.so`（回放）。
Astra 虽是同源芯片组，USB 协议层不同，**必须要 Orbbec 自己的 `liborbbec.so`**。

### 找回驱动

官方 `orbbec/OpenNI2` 仓库已 **404**（停产后删除）。但
**`orbbec/ros2_astra_camera` 还在**，里面带着预编译的 redist：

```
astra_camera/openni2_redist/arm64/OpenNI2/Drivers/liborbbec.so
astra_camera/openni2_redist/arm64/libOpenNI2.so
```

只用 `curl` 取这几个文件，不克隆整个仓库（树莓派走手机热点，省流量）。
下来的是真货：`ELF 64-bit LSB shared object, ARM aarch64`，1.5 MB。

### 两个卡了我一轮的细节

**① Debian 的 libOpenNI2 只认 `lib*.so.0`**

直接把 `liborbbec.so` 拷进系统驱动目录会报：

```
Found no files matching '/usr/lib/aarch64-linux-gnu/OpenNI2/Drivers/lib*.so.0'
```

Debian 打包时改了搜索模式（系统自带那四个驱动全是 `.so.0` 实体 + `.so` 软链）。
文件必须叫 `liborbbec.so.0`。

**② Debian 的 libOpenNI2 与 Orbbec 驱动 ABI 不完全兼容**

放好文件后**枚举成功了**：

```
Device "2bc5/0403@4/8" found.
Uri: 2bc5/0403@4/8 (Vendor: Orbbec, Name: Astra, Product ID: 403)
Serial number: 17122520231
```

对照极干净：**系统 OpenNI2 = 0 个设备，加上 liborbbec.so = 1 个设备。**

但**开流时段错误**。线索在更早的输出里：用 Orbbec 自带的 `libOpenNI2.so` 时
`list_devices` 完整打印了序列号；用 Debian 那版时输出在序列号**之前**就断了。
说明能枚举、深入操作就崩 —— Orbbec 是配着自己那版库测试的。

**解法**：不替换系统库（别的包链接着它），把 Orbbec 的 OpenNI2 整套放在
独立目录，只为相机节点设 `LD_LIBRARY_PATH`（见 `run_camera.sh`）。

### 结果

```
/depth/image      640x480  23.9 Hz  encoding 32FC1 (float32 米)
/depth_raw/image  /ir/image_raw  /projector/camera_info  ...
```

> **教训**：验证要**分层**。先用 `NiViewer2` / `list_devices` 这类
> 不带 ROS 的工具确认"驱动能不能看到设备"，再上 ROS 节点。
> 否则失败时分不清是驱动、ABI 还是 ROS 封装的问题。
> 本次三层各失败一次，正是靠分层才逐个定位。

## 3. 风险 ②：相机是否拖垮平衡回路（已解除）

### 第一次测量是错的

用 `ros2 topic hz` 直接量，得到自相矛盾的结果：

```
相机开：IMU 151.5 Hz，编码器  54.4 Hz
相机关：IMU 112.5 Hz，编码器 131.8 Hz
```

IMU 在相机开着时反而更高。两个问题：

1. **`ros2 topic hz` 自己是个 Python 节点**，订阅开销和调度会污染被测量本身
2. **image_transport 是惰性发布的** —— 没人订阅时驱动只占 2.2% CPU、
   根本不产生帧。"相机开着"和"相机在传数据"是两回事，我测的是前者。

### 正确的做法

录包后**离线统计消息间隔**（测量本身零成本），并且**挂真实订阅者**逼相机出流。
见 `tools/loadtest_camera.sh`。B 段实测 CPU 从 2.2% 升到 15.8%，确认在干活。

### 结果

| | 相机关 | 相机开（23.3 Hz 出流） |
| --- | --- | --- |
| IMU 速率 | 144.0 Hz | **144.0 Hz** |
| IMU 抖动 (std dt) | 0.0043 | **0.0012** |
| 编码器速率 | 99.7 Hz | **99.7 Hz** |
| 编码器抖动 | 0.0053 | **0.0021** |

**吞吐量完全不变，抖动反而更小。** 相机流对控制回路没有可测量的负面影响。
Pi 5 四核，`hfi_imu_node` 32%、`balance_controller` 25%、相机 16%，余量充足。

## 4. 顺带更正一条 07-27 的归因

`max dt` 那一列暴露了别的东西：

```
相机关：IMU max 0.3369 s   编码器 max 0.3301 s
相机开：IMU max 0.0115 s   编码器 max 0.0169 s
```

相机**关着**的 45 秒里出现一次 **340 ms 停摆**，而且
**IMU 和编码器同时卡住**（两个空洞起点相差仅 0.093 s）。

这两个是完全独立的 USB 串口设备（IMU 走 CP2102，编码器走 Arduino），
不可能同时故障。**这是系统级停摆，不是传感器问题。**

> **更正**：07-27 我把一次 344 ms 的空洞记为"IMU 管线偶发停摆"
> （见 `docs/07` 第 11 节 ②），并据此推断问题在 IMU 驱动。
> **该归因作废。** IMU 是被连累的，真正的原因在调度器/内核层面。
> 当时只录了 `/imu/data` 的时间戳去看，没有对照另一路独立数据源 ——
> **单一数据源看不出"共因"**。

与相机无关（相机开着的时段一次都没出现）。发生率仍然很低，
但既然它能掀翻车（07-27 那次就是），值得单独查。
下一步排查方向：`journalctl -k` 看有无内核事件、
CPU 频率/温度节流、以及 WiFi 驱动的中断延迟。

## 5. 风险 ③：制动距离（已测，结果有利）

不需要新实验 —— 前几天遥控数据里每条指令后面都跟着松手，正好是制动过程。
从 `v_ref` 归零那一刻积分轮速直到停住：

| run | 松手时速度 | 停止耗时 | 滑行距离 |
| --- | --- | --- | --- |
| T10 | 0.078 m/s | 0.73 s | 0.035 m |
| slopeA | 0.103 m/s | 0.87 s | 0.049 m |
| T12 | 0.131 m/s | 0.83 s | 0.081 m |
| joydrive | 0.174 m/s | 0.93 s | **0.102 m** |

**最坏 10 cm，停止耗时稳定在 0.9 s。** 距离随速度近似线性，
外推到限速上限 0.25 m/s 约 0.15 m。

**这解除了对 Astra 盲区的担心**：最近感知距离 0.6 m 是最坏制动距离的 **6 倍**。
加上检测延迟（相机 24 Hz = 42 ms，含处理约 100~200 ms，折合 3.5 cm），
总制动距离仍在 0.15 m 量级。按线性外推要让制动距离逼近 0.6 m 需开到约 1.0 m/s，
远超本机物理上限（安全限对应 0.44 m/s）。

> **限定**：这是**正常指令停车**。地面打滑、或撞上前进静摩擦死锁
> （见 `docs/07` 第 11 节 ④），行为不同。避障策略要留安全系数。

## 6. 风险 ④：重力参考系（已实现并验证）

### 问题

TF 树根在 `base_link`，**上面没有任何重力参考**：

```
base_link  ← 根
├── left_wheel / right_wheel   (动态)
├── camera_link → camera_optical_frame  (静态)
└── imu_link                    (静态)
```

所有消费者都隐含假设车身水平。而这是平衡车 —— 站桩时在平衡点两侧摆约 1°，
行驶时外环把它倾到 4°。深度数据因此落在一个**摇晃的坐标系**里，
**平地看起来是斜的**：1 米处 4° 对应 7 cm 的高度误差，
这正好是"地面"和"障碍物"的分界。

### 实现

`balance_bot/level_frame_publisher.py` 发布 `base_link -> base_link_level`，
同原点、**去掉俯仰与横滚、保留航向**（X 仍指向车头方向）。
把深度点变换到 `base_link_level`，高度就是相对重力量出来的。

**刻意没有发布成 `odom -> base_link`**：odom 按约定是世界固定的里程计坐标系，
而这个节点没有位置估计。平移恒为零却叫它 odom，
会误导后续任何期待真实里程计的组件。

IMU 在 URDF 里是 `rpy="0 0 0"`，所以它报的姿态**就是**车身姿态，
不需要再复合一次静态变换（IMU 若改装则此假设失效）。

### 验证方法

读欧拉角**不算验证** —— 车摔倒时的姿态附近欧拉角难以解读且接近万向锁。

无歧义的判据是物理的：加速度计在 `base_link` 里测到重力，
把它按发布的变换旋转过去，**若坐标系正确则必然竖直**，
残余的水平分量就是误差，除以 g 直接换算成残余倾角。
见 `tools/check_level_frame.py`。

**工作区间（车身 5~10°，n=2027）：残差中位数 0.80°，p95 2.07°。**
折合 1 米处 1.4 cm，相对 4° 未补偿时的 7 cm 是够用的。

> **这个测量有个必须说明的局限。** 最初的版本用"合加速度接近 g"来剔除
> 运动样本，实测**拒绝了 0 个样本** —— 不是数据干净，是判据失效：
> 水平加速度与重力**正交相加**，横向加速 0.5 m/s² 只让模长从 9.80 变到 9.81，
> 筛不出来，但它会原封不动进入水平残差。
>
> 所以 **0.80° 是坐标系误差的上界**，其中一部分是车平衡时的真实加速度。
> 要分离两者需改用陀螺判静止，或与已知轮加速度做相关。
>
> （更早还有一版完全没有筛选，报出 67° 的"误差"，实际是操作者把车拿了起来。）

## 7. 下一步

风险 ①~④ 全部解除。剩下的是实现工作，不再有会推翻计划的未知数。

- **深度图 frame_id 对齐**：驱动默认发 `openni_rgb_optical_frame`，
  与 URDF 的 `camera_optical_frame` 不一致，需改参数或加静态变换
- **相机与 IMU 的时间戳对齐**：车身摆动下，深度帧要配对到**当时**的姿态。
  相机 24 Hz、IMU 145 Hz，用 `message_filters` 按时间戳近似同步
- **深度 → 障碍判据**：把点变换到 `base_link_level`，按高度分离地面与障碍，
  输出"最近障碍距离"这类**小数据**（不要把点云推过 WiFi，见下）
- 最后是避障逻辑与状态机

**可视化不要用 RViz 推原始流**：深度图 640x480 float32 @ 24 Hz 约 29 MB/s，
会淹掉 DDS 链路（README 已记过 100 Hz 的 TF 就压垮过热点）。
在树莓派上算、只发小结果；需要看图时离线拉包，或用 `foxglove_bridge`
在浏览器里看（自带压缩限流，且不需要另一台 Linux 机器）。

## 8. 工具选型：哪些值得引入，哪些不要碰

按对**本项目**的实际价值排，不是按名气排。

| 工具 | 结论 | 说明 |
| --- | --- | --- |
| `depth_image_proc` | **马上要用** | 深度图 + camera_info → PointCloud2，不用自己写投影 |
| PlotJuggler | **马上装** | 拖 bag 进去看时间序列和 FFT，探索阶段比写脚本快 |
| Gazebo | **做避障逻辑时引入** | 见下 |
| `robot_localization` | MVP3 的地基 | EKF 融合轮式里程计 + IMU |
| Nav2 | 更靠后 | 见下 |
| `ros2_control` | 不做 | 硬件抽象的"标准做法"，`serial_bridge` 是手搓的简化版。重构过去更正规但**不解决任何现有问题**，纯增复杂度 |
| MoveIt | **完全无关** | 机械臂运动规划。本项目没有任何关节需要规划 |
| SLAM | 不在 MVP2 范围 | 见下 |

### Gazebo：能救什么，救不了什么

**能救**：避障逻辑与状态机。仿真里可以往墙上撞一整天，不用扶车、不怕摔坏。
URDF 已有，接入成本不高。这是它对本项目最实在的价值。

**救不了**：内环整定。前几天遇到的硬问题**恰恰是仿真给不了的** ——
负载静摩擦突破 65~80 PWM、黏滑极限环、IMU 零偏两小时漂 0.86°、
340 ms 系统级停摆、前进卡死在静摩擦以下。这些全是真实世界的脏东西，
而**平衡车恰好是 sim-to-real gap 特别大的品类**，因为动力学被摩擦和延迟主导。

> 用 Gazebo 开发上层逻辑，别指望它调内环。
> 能讲清楚这个区分，比"我用了 Gazebo"本身更值钱。

**前置条件（必须先做，否则仿真里的车会乱飞）**：
当前 URDF 是给 RViz 可视化写的，只有 `<visual>`。
Gazebo 算物理需要补 **`<collision>` 几何**和**靠谱的 `<inertial>`**
（质量、惯量张量、质心位置）。工作量不大但不能跳过。
质心位置尤其关键 —— 它直接决定平衡点，而我们已经实测过真实平衡点在 7.53°，
可以拿来反推校验。

**运行环境**：Gazebo 仿真**完全不需要与树莓派通信**，自成闭环，
所以 DDS 跨机、热点带宽、IP 漂移这些问题一个都不涉及。
Windows 上建议用 **WSL2 + Ubuntu 24.04**（与树莓派同发行版、同为 ROS2 Jazzy，
代码可直接搬），不要用 VirtualBox —— 它的 3D 加速常让 Gazebo 退回软件渲染。
WSLg 能直通 GPU。注意双显卡笔记本上 WSLg 可能挑到核显。
配套版本是 Gazebo **Harmonic**（不是 Gazebo Classic）+ `ros_gz` 桥接。

### Nav2 与 SLAM：为什么不在 MVP2

**避障是无记忆的** —— 每帧独立决策。SLAM 给的是空间记忆
（"回到出发点"、"去某个房间"）。两者解决不同问题，不要混。

不在 MVP2 的四个具体理由：

1. **没有可靠里程计**（SLAM 的先验）。本机还有个特殊麻烦：
   编码器测的是轮子**相对车身**的转动，而车身自己在俯仰，
   地面位移不等于轮转角 × 半径，得先做俯仰补偿
2. **相机视野不适合 SLAM**：水平约 58°、最近 0.6 m。SLAM 通常要 360° 激光
3. **车身持续摇晃**，视觉/深度 SLAM 最怕这个（`base_link_level` 缓解了一部分）
4. **算力**：`rtabmap` 较重，与平衡环抢 CPU 有风险，
   而第 3 节刚验证过相机本身不占资源，不要把这个成果搭进去

Nav2 另有一个平衡车特有的障碍：**它的控制器默认机器人能立刻停下**，
而本机是非最小相位的（要减速得先加速），标准控制器套不上，需改写。
其 **costmap** 部分倒可单独取用做障碍表示。

**正确顺序**：`robot_localization`（里程计+IMU 融合）→ SLAM → Nav2。
顺序颠倒的话会在 SLAM 参数上耗大量时间，而问题根本不在那儿。
