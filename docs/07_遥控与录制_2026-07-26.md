# 遥控控制与 rosbag 录制（MVP1 后半段）

> 2026-07-26。前置：`docs/06_PID调参完全复盘_中文.md`（平衡环整定，已完成）。
>
> 本篇记录在已经能站稳的平衡车上加遥控的全过程：架构怎么改、
> 为什么遥控不需要新回路、失效保护放在哪、以及一路踩下来的坑。

---

## 1. 起点与阻塞点

07-25 收工时车能连续平衡 228 秒，但整个系统只有一个 `/cmd_vel`，
而且它被两个语义完全不同的东西同时占用：

| 谁 | 用 `/cmd_vel` 表示什么 | 单位 |
| --- | --- | --- |
| MVP0 键盘遥控 | 人的速度意图 | m/s、rad/s |
| balance_controller | 给 serial_bridge 的 PWM 指令 | PWM/100 |

`serial_bridge` 订阅 `/cmd_vel` 直接转 PWM 下发。所以**只要平衡控制器在跑，
键盘遥控和它就会抢同一个话题互相覆盖** —— 这是加遥控前必须先解决的事，
不是风格问题。

---

## 2. 话题分层

```
teleop ──/cmd_vel(SI单位,意图)──► balance_controller ──/motor_cmd(PWM/100)──► serial_bridge
                                          │
                                          └──► /balance/state (诊断)
```

实现上没有硬改 `serial_bridge`，而是给 `bringup.launch.py` 加了一个
launch 参数，默认值保持 `/cmd_vel`：

```python
DeclareLaunchArgument('motor_cmd_topic', default_value='/cmd_vel'),
...
Node(package='balance_bot', executable='serial_bridge',
     remappings=[('/cmd_vel', LaunchConfiguration('motor_cmd_topic'))]),
```

`balance.launch.py` 里传 `/motor_cmd` 覆盖它。这样 **MVP0 的键盘直驱用法
一行都不用改**，裸 bringup 依然是 `/cmd_vel` 直通电机。

> 经验：给已有系统加抽象层时，把新语义放在**默认值之外**，
> 旧用法就不会被打断。

---

## 3. 核心洞察：遥控不需要新回路

这是本次最值得讲的一点。

平衡车的串级结构里，速度环和偏航环本来就在**调节两个物理量**：

- 速度环把平均轮速调节到 **0**
- 偏航环把左右轮速差调节到 **0**

"站着不动"只是"设定值为 0"的一个特例。所以遥控要做的不是新增控制器，
而是**把这两个 0 换成指令值**：

```python
vel_err  = self.wheel_velocity - self.v_ref      # 原来隐含 v_ref = 0
turn_err = self.turn_velocity  - self.turn_ref   # 原来隐含 turn_ref = 0

offset_trim     = kp_v * vel_err + ki_v * self.velocity_integral
sync_correction = wheel_sync_kp * turn_err
```

改动就是两行里各加一个减号项。已经整定好的增益**完全不用重调**，
因为回路的动力学没变，只是工作点移了。

## 4. 单位换算（从已有标定量推，不重新测）

| 量 | 来源 | 值 |
| --- | --- | --- |
| 编码器分辨率 | `serial_bridge` 的 `ticks_per_rev` | 277.5 计数/圈 |
| 轮半径 | URDF `cylinder radius` | 0.0325 m |
| 轮距 | URDF 左右轮 joint origin ±0.11 | 0.22 m |

```
周长 = 2π × 0.0325 = 0.2042 m
ticks_per_meter = 277.5 / 0.2042 = 1358.9        → 1 m/s = 1359 ticks/s
```

节点启动时会把这个数打出来自检，实测日志 `1358.9 ticks/m`，与手算一致。

**由此得到一个重要约束**：安全限 `max_wheel_velocity = 600 ticks/s`
换算过来只有 **0.44 m/s**。而 `teleop_twist_keyboard` 默认速度是 0.5 m/s，
直接超限。所以指令**必须在控制器内部钳位**，不能信任输入源。

偏航换算（差速驱动）：

```
v_left = v - ω·L/2 ,  v_right = v + ω·L/2
turn   = v_left - v_right = -ω·L
turn_ref[ticks/s] = -ω · 0.22 · 1358.9 = -299 · ω    → 1 rad/s = 299 ticks/s 差模
```

负号来自 REP-103：`angular.z` 为正是**左转（逆时针）**，左转时右轮更快，
所以差模设定值取负。台架实测 +0.5 rad/s 得到 `turn_ref = -149.5`，
与 `-0.5 × 0.22 × 1358.9 = -149.5` 完全吻合。

## 5. 失效保护三件套

平衡车上遥控失效不是"停下来"，是"摔倒"，所以这部分比功能本身重要。

**① 指令超时回零**（`cmd_timeout_s: 0.5`）
断连、teleop 进程崩溃、手柄没电、Wi-Fi 抖动 —— 任何一种都会让
`/cmd_vel` 停发。此时设定值斜坡回零，**车原地继续平衡**，
而不是保持最后的速度冲出去。

> 这条决定了失效保护必须做在**控制器里**，而不是指望输入端。
> 手柄的死人开关是第二道防线，不是第一道。

**② 设定值斜坡限速**（`cmd_accel_ticks_s2`）
阶跃指令要求车身瞬间改变倾角，非最小相位系统做不到。见第 8 节实测。

**③ 幅值钳位**（`max_cmd_linear_mps: 0.25`、`max_cmd_angular_rps: 1.2`）
无论上游发什么，进环的设定值都在物理可承受范围内。

另外**未接管时输出硬零**：实测在车躺在地上、持续发
`{linear.x: 0.2, angular.z: 0.5}` 的情况下，`/motor_cmd` 全零。

## 6. `/balance/state` 诊断话题

改造前，离线分析必须**重放控制器状态机**才能还原哪些时段在平衡
（`analyze_run.py` 的做法）。现在控制器直接把自己的内部视角发出来：

```python
STATE_FIELDS = ('pitch','err','rate','trim','offset','vel','vel_raw','turn',
                'v_ref','turn_ref','vel_int','u','sync','engaged')
```

用 `Float32MultiArray`，字段名写进 `layout.dim[0].label`，
**包本身是自解释的**，不依赖源码版本。48 Hz（IMU 帧率 3 分频）。

这一步的收益在第 8 节体现得很直接：后退超调的机理，是靠逐点打印
`v_ref / vel / trim / err / u` 一眼看出来的 —— 靠聚合统计看不见。

## 7. rosbag 录制集成

```bash
ros2 launch balance_bot balance.launch.py record:=true bag_name:=teleopT5
```

launch 里用 `ExecuteProcess` + `IfCondition` 挂 recorder，自动附加时间戳、
mcap 格式、固定 6 话题（`/imu/data /wheel/encoders /joint_states
/cmd_vel /motor_cmd /balance/state`）。省掉每次手敲话题清单，
也保证每个包的话题集一致、可比较。

## 8. 遥控整定实录

测试用 `tools/teleop_sequence.py`：前进 / 后退 / 左转 / 右转，
各 3 秒，间隔 6 秒（间隔同时在验证指令超时）。

### T1 — 测出来的是测试脚本的 bug

分析报告只有两个偏航指令块，两个直线指令块**完全没有**。
但包里明明录到了 34 条 `linear.x=0.08`。

进一步查：`v_ref` 全程精确为 `0.000000`，控制器日志里"遥控指令接入"
只出现 **2 次**（应该 4 次）。

**根因**：测试脚本用 shell 循环套 `ros2 topic pub`，每条指令一个新进程。
`ros2 topic pub` 在 DDS 发现匹配上已有订阅者**之前**就开始发，
VOLATILE 语义下这些消息对尚未被发现的订阅者直接丢弃。
录包节点被发现了，控制器没有 —— 于是包里有数据，回调一次没触发。

**修复**：改成常驻单 publisher，且在 `get_subscription_count() > 0`
之前不发任何消息（`tools/teleop_sequence.py`）。

> 教训：**"发出去了"和"收到了"是两回事**。rosbag 记录的是录包节点
> 收到的，不等于目标节点收到的。验证链路要看接收端的证据。

### T2 — 台架验证（车躺地上，未接管）

把设定值斜坡改成与接管状态无关后，可以在车不动的情况下验证整条指令链路：

| 指令 | 期望 | 实测 |
| --- | --- | --- |
| 前进 0.08 m/s | +108.7 ticks/s | **+108.7** |
| 后退 0.08 m/s | −108.7 | **−108.7** |
| 偏航 ±0.5 rad/s | ±149.5 | **±149.5** |
| 斜坡 250 ticks/s² | 0.43 s 到位 | ~0.4 s |
| 超时回零 | 0.5 s 后衰减 | ✓ |

`engaged` 全程 0，电机硬零。**能在不冒摔车风险的情况下验证的东西，
就不要在车上验证。**

### T3 — 第一次真正行驶

4 条指令全部生效。但出现两个问题。

**问题 A：跑飞保护误触发 3 次**

```
raw=-639.1  filtered=-306.8
raw=-620.6  filtered= -71.7    ← 滤波后几乎静止
raw=+818.3  filtered= +51.6    ← 滤波后几乎静止
```

原判据用的是**未滤波**轮速。而 277.5 计数/圈、10 ms 窗口下，
**一个计数就是约 100 ticks/s**，raw 信号逐帧在 0 和 ±300 之间跳。
包里 raw 峰值 687、滤波后仅 356。

**修复**：判据改用滤波轮速。时间常数 `dt/alpha = 0.01/0.06 ≈ 0.17 s`，
真跑飞仍能在 0.3 s 内切断，且上面还有 12° 倾角保护兜底。

> 保护判据应该看**持续量**，不是单帧尖峰。这个 bug 在整定阶段就存在，
> 只是原地站桩时轮速小、没暴露出来。

**问题 B：后退超调 190%**（v_ref −98 → vel −283）

**修复尝试**：斜坡 250 → 120 ticks/s²。

### T4 — 斜坡修复只治好了一半

| 指令 | v_ref | 实测 vel | 跟随 |
| --- | --- | --- | --- |
| 前进 | +87.8 | +91.6 | **104%** ✓（T3 是 130%） |
| 后退 | −88.3 | −266.5 | **302%** ✗ |
| 左转 | −139.7 | −120.1 | 86% |
| 右转 | +140.7 | +92.8 | 66% |

保护误触发从 3 次降到 1 次，且整段序列在**单次 120 秒接管**内跑完。
前进被治好了，后退没有 —— 说明后退不是斜坡问题。

**逐点数据揭示：这根本不是"超调"，是稳态。**

```
t=744.9 … 746.6   v_ref=-108.7   vel≈-275   trim≈+1.35   u≈-50..-80（未饱和）
```

`vel` 稳稳停在 −275 长达两秒。验算：

```
vel_err = -275 - (-108.7) = -166
kp_v × vel_err = -0.008 × -166 = +1.33     ← 与实测 trim +1.35 吻合
```

**回路完全在按设计工作**，问题在结构：行驶时我把积分泄放掉了
（为了避免松手倒车找位置），速度环退化成**纯 P**。
纯 P 无法消除稳态扰动，只能用误差换力矩。

后退需要 **+1.43° 的常驻前倾**才能维持那个速度；kp_v = −0.008
要产生 +1.43°，就必须**允许** 179 ticks/s 的误差。
前进需要的 trim ≈ 0，所以前进跟随 104%。
**跟随度的不对称，就是所需 trim 的不对称除以一个太小的增益。**

### T5 — 给速度环补回积分权限

`drive_integral_leak_s: 0.5 → 3.0`。

泄放积分的稳态是 `I = τ · vel_err`，于是等效增益：

```
kp_v + ki_v·τ = -0.008 + (-0.005 × 3) = -0.023      约 3 倍刚度
```

**可证伪预期**：同样需要 +1.43° trim，误差应从 179 降到
`1.43 / 0.023 ≈ 62` ticks/s，后退实测速度应落在 **−150 附近**（而非 −275）；
前进本就不需要 trim，应基本不变。

**结果：这一轮作废，但作废的原因本身很值得记。**

车在序列开始前 3 秒就摔了（接管段 281.1→304.8 s，第一条指令在 308.1 s），
所以四个"指令块"全是零 —— 那是电机已断电后的记录，不是跟随失败。

先说一个**我判断错了又自己纠正**的过程，因为纠正的方法比结论更有用。

摔倒瞬间的数据长这样：

```
304.5   vel -54.3   trim 1.76   err -0.59   pitch  8.71   u  -33.3
304.6   vel -51.2   trim 1.76   err -3.92   pitch  5.36   u -255.0
304.6   vel -52.2   trim 1.76   err -9.36   pitch -0.07   u -255.0
304.7   vel -220.1  trim 3.16   err -12.83  pitch -2.15   u -255.0
```

pitch 在约 0.2 秒内从 8.71° 掉到 −2.15°，而**轮速几乎不动**（−54 → −52）。
我的第一反应是机械失效：车身相对轮轴转了，而轮子没动，只有连接件松脱
才会这样；何况本项目有两次紧固件松动前科。

**但在下结论前先查了采样间隔**：

```
    t          dt      pitch
 304.5298   0.3637      8.71     ← 364 ms 没有数据
 304.5359   0.0061      8.72     ← 之后 11 帧挤在 27 ms 内
 304.5412   0.0053      8.35
 ...
 304.5629   0.0024     -0.07
```

不是机械失效，是 **IMU 管线停摆 0.36 秒后缓冲区一次性倾泻**。
控制器在那 1/3 秒里**没有任何新数据**，一直输出停摆前算出的 `u≈-33`，
车就在瞎着的时候倒了。所谓"0.2 秒塌陷"其实是 **0.36 秒的真实动作
被压缩进 27 ms 回放**。

进一步统计四轮全部 IMU 消息：

| run | 消息数 | 速率 | 中位 dt | p99 | 最大 dt |
| --- | --- | --- | --- | --- | --- |
| T1 | 36632 | 147 Hz | 0.0060 | 0.0081 | 0.010 |
| T3 | 71981 | 145 Hz | 0.0061 | 0.0082 | 0.010 |
| T4 | 121127 | 145 Hz | 0.0061 | 0.0082 | 0.010 |
| T5 | 66644 | 144 Hz | 0.0061 | 0.0082 | **0.344** |

**约 29.6 万条消息里只有这一次间隔超过 10 ms。** 偶发，不是慢性病。

> **方法论**：看到"突变"先问一句**采样是不是连续的**。
> 时间轴上的空洞会把缓慢过程伪装成瞬间事件，进而把软件问题伪装成硬件问题。
> 判据很简单：查 dt。这一步花了两分钟，省下的是拆车的时间。

对控制器本身无需改动：停摆期间控制器不发布，`serial_bridge` 的
0.25 s 看门狗会自动清零 PWM。364 ms 的盲区对平衡车是致命的，
任何控制律都救不回来，真正的解法在 IMU 驱动的健壮性，
但 1/30 万的发生率暂不值得投入。

### T7 — 冷机：温漂假设的判决性实验

隔夜断电冷却后重新开机（开机 3 分钟内采数）：

```
冷机平均 pitch   7.532°        配置 offset 7.53
偏差            +0.002°        ← 前一晚收工时是 -0.49°
velMean         -0.5 ticks/s   （近零，均值才有意义）
velInt mean     +9             （近零，不限幅）
连续平衡        351.2 秒       （零故障，停录制时仍在站）
```

**温漂假设成立**：前一天两小时单调滑掉的 0.86° 完全归零。

一句限定：电池同时被充过。但电压**无法解释这个现象** ——
漂的是 IMU *测出来的* pitch，电压既不移动重心也不改变 IMU 读数，
它只影响电机权限（表现为误差与出力变大，不是平衡点位移）。
故机械方向可以排除。

同口径误差对比也随之闭环：

```
A10 (07-25):  errRMS 0.30~0.31°   range [-0.95,+1.00]   |u| peak <70
T8  (冷机)  :  errRMS 0.34°        range [-1.27,+1.13]   |u| p99  66
```

前一天"errRMS 退化到 0.50"确系跑热后平衡点偏移所致，控制器本身没有变差。

### T8 — 后退修复验证（leak 3.0）

| 指标 | T4 (leak 0.5) | T8 (leak 3.0) |
| --- | --- | --- |
| 连续平衡 | 120.4 s | **361.2 s（全程 100%）** |
| 故障 | 1 | **0** |
| 后退跟随 | −266.5（302%） | −157.6（179%） |
| 前进跟随 | +91.6（104%） | +113.2（128%） |

预测 −150，实测 −157.6，差 5%。机理确认。

**但暴露出一个真正的遥控缺陷**：净位移 **+0.01 rev** ——
车精确地回到了出发点。前进指令结束 5 秒后倒退了 277 mm。

原因不是残留积分（指令结束瞬间 `vel_int` 只有 +19，折合 trim 跳变 0.1°），
而是**指令结束后积分重新累积**：此刻车位移在原点前方 1.11 rev，
位置环的职责就是把这个位移积回零。
遥控要的是"停在你把它开到的地方"，不是"回到原点"。

修法：`reset_integral_on_stop` —— 从行驶切回站桩的那一刻清零位置积分，
等于把当前位置定义为新的保持点。

### T9 — 位置保持点修复：有得有失

净位移 +0.01 → **−2.43 rev**，车不再爬回原点 ✓

但后退跟随从 −157.6 退到 −225.8。

**原因是 T8 那个数被污染了**：前进指令结束后积分累积到 −148，
这份残留在随后的后退指令里恰好提供了额外制动。清零后这份"免费帮助"消失，
**−225.8 才是干净的真实值**。

> 这类"修复导致指标退步"的情况要先问：**退步的那个指标，
> 之前的好成绩是不是靠某种副作用得来的？** 是的话，退步反而说明修对了。

### T10 — 最终配置（leak 6.0 + 位置重置）

既然位置重置已经消除了长泄放时间常数的副作用，两者就是互补的：
**长泄放买行驶期的跟随权限，重置阻止这份权限事后把车拖回旧位置。**

| 指标 | T9 (leak 3.0) | **T10 (leak 6.0)** |
| --- | --- | --- |
| 后退跟随 | −225.8（257%） | **−71.3（81%）** |
| 前进跟随 | +128.9（146%） | **+107.3（122%）** |
| 左转跟随 | — | −127.5 / −140.1（**91%**） |
| **峰值 PWM** | 255（饱和） | **95.3** |
| 误差范围 | [−2.02, +1.50] | **[−1.05, +1.24]** |
| 接管率 | 201/203 s | **276/276 s** |

**跟随变好的同时峰值出力从饱和的 255 掉到 95** —— 这是控制质量真正改善的
标志，而不是拿力气换精度。

预测 −126、实测 −71.3，**量级预测偏了**（方向和数量级对）。
原因：+1.43° 那个"所需常驻倾角"是在差跟随条件下测的，
跟随一好速度就低、扰动也小，线性外推自然偏。

**遗留**：右转跟随仅 28%（左转 91%），偏航方向存在明显不对称，见 T11~T13。

### T11~T12 — 偏航修复 + 零点自适应

**偏航根因不是增益不够，是限幅卡在静摩擦以下。**

```
左转   sync 均值  +8.2                    ← 车本身偏左，只需一点点
右转   sync 均值 -34.3   峰值 -59.2       ← 1% 采样顶到 60 上限
                                            而实测负载突破 PWM 是 65~80
```

`0.4 × 误差 = sync` 两方向都精确吻合，**P 律一直在正确执行**，
但右转所需修正量整个生命周期都在突破阈值以下，轮子挣不脱。

修法：`max_wheel_sync_pwm` 60 → 110（越过突破电压），
外加泄放积分 `wheel_sync_ki=0.08` / `turn_integral_leak_s=6.0`
（等效低频增益 0.4 + 0.08×6 = 0.88）。用泄放而非纯积分，
是为了误差消失后自行衰减、不锁死航向。

结果：**右转 28% → 91%，左转 91% → 99%。**

并且确认**没有串扰**：直线指令期间 sync 峰值仅 18（老配置是 24），
比修改前还安静 —— 提高偏航权限没有污染直线通道。

**零点自适应**（`offset_adapt_tau_s=120`）：站桩且平均轮速为零时，
速度环平均要顶住的 trim 就等于零点误差，慢慢把它吸收进 `offset_bias`。

同口径对比：

| | T10 | T12 |
| --- | --- | --- |
| 站桩 errRMS | 0.59° | **0.38°**（历史最好） |
| 站桩 trimMean | +0.356 | **+0.046** |

`trimMean` 逼近零就是自适应生效的直接证据。

> **两个统计陷阱，都是被用户当场纠正的：**
>
> 1. 我用 `grep -c '已接管'` 数出"17 次摔倒"，用户说只摔了两次。
>    `latch_on_fall: false` 下，扶车过程中车会反复穿过接管窗口，
>    **一次物理摔倒能刷出好几行日志**。正确做法是数
>    *持续时间足够长的接管段之间的中断*（已加进 `analyze_teleop.py`）。
>    我基于错误计数说过"这个特性有害"，那个判断作废。
> 2. 我报告 T12 站桩 errRMS 0.88 是"退步"，实际是被一段 45 秒的
>    摔倒数据污染了；剔除后是 0.38，反而是历史最好。
>    **分段统计前先确认每段的状态是同质的。**

### T13 — 行驶抖动

用户反馈"前进后退时存在抖动"。频谱直接定位：

| | 主频 | u 峰峰值 |
| --- | --- | --- |
| 前进 | **9.18 Hz** | **397 PWM** |
| 后退 | **9.18 Hz** | 394 PWM |
| 站桩 | 0.32 Hz（慢摆） | 156 PWM |

行驶时输出几乎在 ±200 PWM 之间来回甩。站桩看不出来，是因为
车身动作小、激励不足；一行驶，静摩擦反复挣脱就是宽带激励，
把回路在自激点上"敲响"。

D 项嫌疑：`pitch_rate_filter_alpha=0.3` 在 145 Hz 下截止约 6.9 Hz，
振荡在 9.2 Hz —— 正好在截止之上，滤波器已开始产生相位滞后。
估算 9.2 Hz、±0.3° 振荡对应角速度 17 °/s，乘 `kd=5` 就是 86 PWM，
D 项在该频率上是主导项。

改 `pitch_rate_filter_alpha: 0.3 → 0.15`（截止降到 3.5 Hz）：

```
前进 err 主频  9.18 Hz → 0.46 Hz    车身抖动消失
后退 err 主频  9.18 Hz → 7.07 Hz    err RMS 0.63 → 0.45
```

> **关键诊断：振荡频率跟着滤波系数一起移动了（9.18 → 7.07 Hz）。**
> 这一条排除了机械谐振 —— 结构谐振的频率由结构决定，
> 不可能因为改一个软件系数就变。所以是**控制回路自激**，
> 自激点由 D 通道的相位滞后决定。
>
> 推论：改滤波只能把自激点挪低，要消除必须降低该频率上的环路增益
> （降 `kd`），或者从根上换掉信号源 —— 用陀螺原始
> `angular_velocity.y` 代替 pitch 差分，就没有微分噪声，
> 也就不需要这么重的滤波，相位裕度直接改善。**后者是真正的解法。**

## 9. 踩过的坑（工程环境类）

这几个都跟控制无关，但都真实浪费了时间，值得记。

**① `pkill -f` 会匹配到自己**

```bash
ssh pi "pkill -f balance_controller"     # 命令行里含 "balance_controller"
```
pkill 匹配全命令行，**把自己所在的 ssh shell 也杀了**，后续命令不执行。
结果两套 stack 同时在跑、两个 `serial_bridge` 同时写 Arduino 串口，
IMU 报 "multiple access on port"。

改用括号写法：`pkill -f '[b]alance_controller'` —— 正则匹配
`balance_controller`，但字面量 `[b]alance...` 匹配不到自己。

**② 非交互 shell 的后台任务忽略 SIGINT**

POSIX 行为：非交互 shell 里以 `&` 启动的后台任务会继承 `SIGINT = SIG_IGN`。
所以 `kill -INT` 停不掉 rosbag recorder，**metadata.yaml 不写，
整个包读不了**。必须用 `SIGTERM`。

**③ ssh 后台进程会挂住 ssh 会话**

`nohup ... &` 不够，ssh 会等 channel 关闭。要 `setsid nohup ... < /dev/null > log 2>&1 &`，
且 stdin 重定向不能省。

**① IMU 零偏随通电时间漂移（已确认，未处理）**

| run | 时间 | 平衡段平均 pitch | 相对 offset 7.53 |
| --- | --- | --- | --- |
| T1 | 07-26 15:47 | 7.895° | +0.37° |
| T3 | 07-26 16:15 | 7.706° | +0.18° |
| T4 | 07-26 16:59 | 7.287° | −0.24° |
| T5 | 07-26 17:22 | 7.039° | **−0.49°** |
| **T7** | **07-27 10:27（冷机）** | **7.532°** | **+0.002°** |

连续会话内单调漂移 0.86°，**断电冷却一夜后完全归零**。
关键特征是单调 —— 既排除随机噪声，也不像紧固件松动（松动是突变）。

影响：跑热后 offset 偏了，站桩 errRMS 从 0.31° 劣化到 0.50°，
且行驶时的方向不对称被放大。

处理思路（按代价排序）：
(a) `capture_offset_on_engage` —— 每次接管时重新捕获平衡点，
    机制已存在且已实现（`capture_settle_time_sec` / `capture_rate_below_dps`），
    目前关闭。代价最低，但每次接管的捕获值本身有噪声；
(b) 让速度环积分在长时间尺度上吸收零偏（等价于在线估计），
    需要把站桩积分的时间常数拉得很长且做好抗饱和；
(c) 读 IMU 温度输出做补偿，最彻底但要先确认 HFI-A9 是否输出温度。

**② IMU 管线偶发停摆**

实测 29.6 万条消息中出现一次 344 ms 空洞，足以让平衡车摔倒
（详见第 8 节 T5）。发生率约 1/30 万，暂不处理，但需知道
**它存在，且症状会伪装成机械失效**。
与 06 篇遗留的"IMU 速率从 303 Hz 掉到 ~147 Hz 未解释"可能同源。

**③ 行驶抖动：7 Hz 回路自激（部分缓解，未消除）**

已确认是控制回路自激而非机械谐振（依据见 T13：频率随滤波系数移动）。
`pitch_rate_filter_alpha` 降到 0.15 后前进抖动消失、后退降到 7.07 Hz。

> **⚠️ 更正：06 篇遗留项里"用陀螺原始 `angular_velocity.y` 替代 pitch 差分"
> 这条建议，在本机上是错的，已被实测推翻。不要照做。**

轴向标定可以**直接从已录的包离线做**，`/imu/data` 本来就带 `angular_velocity`，
不需要碰硬件。把三轴分别与 pitch 差分做相关（T12 包，13.6 万样本）：

```
angular_velocity.x :  r = -0.063     无关
angular_velocity.y :  r = +0.835     就是它，符号为正，不需取反
angular_velocity.z :  r = +0.031     无关
```

轴向和符号都确认了。但**换过去会让抖动更严重**，因为陀螺那一路是滞后的：

```
谱分析   6~9 Hz 幅值比 1.02，相位 d(pitch)/dt 超前陀螺 +50.6 度
互相关   峰值在 -3 采样 = -18.1 ms（r 由零延迟 0.813 升到 0.946）
交叉验证 18 ms 在 7.7 Hz 处 = 0.018 x 7.7 x 360 = 50 度，与谱分析吻合
```

**四元数推出的 pitch 角速度比陀螺读数早 18 ms**，推测是 HFI-A9 片上融合对
四元数做了预测，而角速度那一路多过了一层低通。换成陀螺等于在自激点上
再叠 50 度相位滞后，只会更糟。

（顺带纠正一个统计细节：最初用 `polyfit(gyro, dpitch)` 得到斜率 0.82，
看着像幅值衰减。那是**自变量带噪声导致的回归衰减偏差**；
谱比给出的 1.02 才是无偏结果。**自变量有噪声时不要用回归斜率估增益。**）

**所以剩下的路是降低自激频率处的环路增益** —— 降 `kd`。**已验证，有效。**

同一次会话内背靠背对比（第 1 轮 kd=5.0，第 2、3 轮在线改成 3.5，
不重启不重扶，地面位置和温度都相同）：

| 序列 | kd | 前进 err 主频 | 前进 u 峰峰值 |
| --- | --- | --- | --- |
| 1 | **5.0** | **7.00 Hz** | **356.5** |
| 2 | 3.5 | 0.45 Hz | 146.7 |
| 3 | 3.5 | 0.44 Hz | **127.4** |

kd=3.5 的所有指令段里 `err` 主频都回到 0.44~0.45 Hz（本来就有的慢摆），
**7 Hz 分量从车身运动里彻底消失**，输出峰峰值降到三分之一。

代价检查（降 kd 等于减阻尼，必须确认平衡质量没被牺牲）：

| 窗口 | kd | 站桩 errRMS | 误差范围 | \|u\| p99 |
| --- | --- | --- | --- | --- |
| 120-150s | 5.0 | 0.35 | [−1.19, +1.21] | 65 |
| 280-315s | 3.5 | 0.38 | [−1.11, +1.51] | 79 |
| 360-400s | 3.5 | **0.34** | [−1.05, +1.43] | 71 |

**0.34~0.38 对 0.35，在 run-to-run 噪声以内。** 让出去的那部分阻尼，
本来就只是在喂养振荡。

> 中间有个窗口（200-235s）测出 errRMS 0.81、误差范围 [−11.88, +2.91]，
> 看着像 kd=3.5 严重变差。查了一下，那段**跨了一次摔倒**（接管段在 205.8s 断开）。
> 又一次同样的陷阱：**分段统计前先确认每段状态同质**。

**结论**：抖动问题收敛。若将来还需进一步压制，再考虑 D 通道加 7 Hz 陷波器。

**④ 直线跟随率不可重复 —— 大概率是测量方法的问题，不是控制问题**

> **2026-07-27 更新：下面"环境扰动/地面坡度"的推断已被 180 度实验推翻。
> 当前判断是测量窗口太短。**

**180 度判决实验**（同一位置，只把车原地转 180 度，各跑一轮）：

```
              bias(站桩)          trimMean   平均时长
A 原朝向      +0.390 -> +0.413    +0.035     184 s
B 转 180 度   +0.384 -> +0.418    +0.032     203 s
```

零点自适应开着时，坡度所要求的常驻倾角会被吸收进 `offset_bias`，
所以 **`bias` 才是坡度指示器**（`trimMean` 被自适应按设计压到零，不能用）。
两个朝向的 bias **相差 0.005 度** —— 有坡的话应该相差两倍坡度角。
**地面坡度排除。**

原先基于指令段 trim 做的"共模/差模"分解**不可信**：它假设指令段达到了稳态，
而实际没有 —— B 轮后退指令下车竟然朝前走了 +34.5（设定值 −88），方向都反了，
那个 trim 数值不代表任何"所需常驻倾角"。

**真正的嫌疑：测量窗口短于被测信号的周期。**

车有一个 **0.45 Hz 的慢摆模态**（周期 2.2 s，每一轮数据里都稳定出现）。
而指令只有 3 s，取"后半段"平均就是 **1.5 s，不到一个完整摆动周期**。
在一个正在摆动的量上取不足一周期的平均，结果完全取决于恰好落在哪个相位。

佐证：跟随率在 8 轮 20 条指令里从 4% 跳到 302%（75 倍），
而**同一批数据里所有其它指标都高度可重复** ——
站桩 errRMS 0.34~0.38、bias、偏航跟随 91%/99% ——
**唯独这一个指标不稳定，也唯独它的测量窗口短于被测信号周期。**

指令起始时刻的速度只解释了一小部分（r ≈ −0.43，n=10，不显著）。

**已执行**：指令时长 3 s → 12 s（`HOLD_S`），并按 2.2 s 子窗口拆开看。
结果部分推翻了"测量假象"的判断，而且挖出了真正的原因。

```
12 s 指令，各 2.2 s 子窗口的跟随率：
  前进   127  65   0   0   0     <- 走约 4 秒后彻底停死
  后退   128 132 137 162 145     <- 高度一致
  左转    89  71  70  43
  右转    64  94  64  51
```

后退的一致性证明**加长窗口确实让测量稳定了**（原来 3 s 窗口下同一条指令
在各轮之间从 179% 跳到 302%）。但前进不是相位散布，是**真的停住**。

### ④ 真正的原因：低误差死锁（stall lock）

前进指令下停住时的逐点状态：

```
t=155~160s   v_ref +108.7   vel 0.0   vel_raw 0.0（100% 采样为零）
             trim +0.84     err +0.15  pitch 8.96   u ~ 14
```

机理：

1. 速度环发现没到设定速度，把目标倾角抬高到 `trim +0.84`
2. **车身照做了** —— 前倾到 pitch 8.96 正好对上新目标
3. 于是角度环误差只剩 `err = 0.15 度`，它认为一切正常，
   输出塌缩到 **u ~ 14 PWM**
4. 而实测负载静摩擦突破电压是 **65~80 PWM** —— 14 推不动轮子
5. 车前倾着站在原地不动，**形成稳定的死锁平衡**

关键在于回路**没有能力自己escalate**：`drive_integral_leak_s = 6.0`
让位置积分在行驶时持续泄放（实测 `vel_int` 从 28 衰减到 4），
trim 停在 +0.84 再也涨不上去，永远够不到突破电压。

**这解释了跟随率 4%~302% 的巨大方差**：不是相位噪声，
是"这一轮卡住了没有"的二元结果。后退不卡，前进卡。

也和 06 篇的静摩擦结论对上了：那里实测出负载突破 65~80 PWM，
并把静摩擦前馈列为"暂缓"，理由是共模前馈会先松开一个轮子而表现为偏航。

**候选解法**：

(a) **失速时冻结泄放** —— 判据 `|v_ref| > deadzone 且 |vel| ~ 0`，
    让积分正常累积把 trim 顶上去，直到轮子挣脱。
    **已实现并实测 —— 失败，已禁用（`stall_velocity_ticks: 0`）。见下。**
(b) 静摩擦前馈，**必须在左右分流之后逐轮施加**（06 篇的结论）。
(c) 低速抖动（dither），代码里已有 `deadband_dither_hz` 骨架，目前关闭。

### (a) 的失败：用错了执行机构

它**确实挣脱了死锁**，但把系统推进一个发散的极限环：

```
t=295.9  指令未到    vel_int 已 -254   trim +1.68   <- 站桩时就攒了这么多
t=297.1  指令开始    vel_int -281                    （判定失速，继续累积）
t=298.3  挣脱        vel +342.9                      <- 设定值 108.7，冲到 3.2 倍
t=305.1  反冲        vel  -43.2   trim +1.67
t=307.5  更猛        vel -202.8   trim +2.88
```

卡住 → 积分猛涨 → 挣脱 → 暴冲 3 倍 → 过冲修正 → 又卡住 → 循环，
日志里滤波轮速逐轮从 −606 爬到 −1300，是发散不是收敛。

**根本错误在于执行机构选错了，不是数值没调好。**
积分是**秒级的慢状态**；用它去顶穿**毫秒级**的静摩擦突破，
等轮子一动，积分还挂在 −290 上、泄放时间常数 6 秒收不回来，
车就继续加速冲过头。时间尺度根本不匹配。

**正确的方向是作用在输出上**：检测到"要动而没动"时直接在 PWM 上加一个
刚好够突破的量，轮子一动立刻撤掉，**不留任何残留状态**。
也就是方案 (b)。

> 这条负结果值得留着：它给出了一个可复用的判据 ——
> **补偿一个快过程，就得用快执行机构。**
> 慢积分器能改变工作点，但不能用来穿越阈值。

**注意**：`reset_integral_on_stop` 只在指令**结束**时清零，
救不了指令**进行中**的失控，所以它对 (a) 的发散没有帮助。

**（以下为已被推翻的原推断，保留以记录推理过程）**

**~~直线跟随的方向不对称：环境扰动，非控制器缺陷~~**

各轮**参数完全相同**，但后退所需的常驻 trim 差 3.4 倍，
而跟随率精确地跟着它走：

| run | 后退实测 | 跟随 | 所需 trim |
| --- | --- | --- | --- |
| T4 | −266.5 | 302% | +1.43° |
| T9 | −225.8 | 257% | +1.23° |
| T12 | −228.2 | 259% | +1.22° |
| T8 | −157.6 | 179% | +0.82° |
| T10 | −71.3 | **81%** | **+0.42°** |

**T10 是异常值，不是常态。** 同一天同一房间、同一套参数下所需 trim
能差 3 倍，说明它不是机器的固有属性，而是**环境扰动**——
最可能是地面坡度（每次扶车放下的位置和朝向都不同）。

**判决实验（未做）**：同一位置跑一次序列，然后把车**原地转 180°** 再跑一次。
trim 需求跟着翻号 → 地面坡度；不翻号 → 车本身（重心偏置或摩擦不对称）。
五分钟可定案，需人配合转车。
